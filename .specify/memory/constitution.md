# IVR Platform Constitution

## Core Principles

### I. API-First & Asynchronous Architecture
The platform is built on modern asynchronous frameworks (FastAPI for backend/API, FastAGI for Asterisk). All I/O operations (database, Redis, HTTP requests) MUST utilize async/await to maximize throughput and prevent blocking the event loop.

### II. Stateless Handlers & External State Management
Call sessions and flow execution states MUST NOT be stored in local memory. All active call state, variables, and tracking must be managed externally in Redis with appropriate TTLs. Permanent records (CDRs) are stored in PostgreSQL upon call completion.

### III. Multi-Tenant Isolation
The platform is strictly multi-tenant. Every entity (Flows, Calls, Audio Assets) MUST include and be filtered by a `tenant_id`. No cross-tenant data access is permitted.

### IV. Visual Flow Driven Execution
IVR logic is strictly data-driven via JSON definitions generated by the ReactFlow frontend. The backend AGI flow engine acts only as an interpreter of these definitions. Hardcoded IVR logic in the backend is prohibited; logic must be expressed through standardized step types (e.g., `play_audio`, `collect_dtmf`, `api_call`).

### V. Robust Audio Resolution Hierarchy
Audio playback MUST adhere to the strict fallback resolution strategy to ensure callers always hear a prompt: Step-Specific Audio -> Flow Default -> Tenant Default -> System Default -> Text-To-Speech (TTS) Fallback.

## Architecture & Technologies

- **Frontend**: React, ReactFlow (Flow Builder), Material UI.
- **Backend**: FastAPI (Python), Asterisk FastAGI integration (`asterisk-agi`).
- **Database**: PostgreSQL (via `asyncpg` / SQLAlchemy).
- **Cache/State**: Redis (via `redis-py` async client).
- **Telephony**: Asterisk PBX with SIP/AGI configuration.

## Development Workflow

- All new IVR step types must be implemented in both the React Flow Builder (as a node type with configuration UI) and the Python FastAGI Flow Engine (as a step handler).
- Asynchronous database interactions should use the connection pool context manager (`get_db`).
- Changes to the flow definition JSON schema must be strictly versioned and backward compatible with existing calls/flows.

## Governance

All PRs/reviews must verify compliance with the Core Principles. Architectural changes (e.g., introducing a new state store, changing the flow schema) require an amendment to this Constitution. Complexity must be justified, particularly regarding Asterisk integration and real-time state management.
